Power Consumption of Operating Vision-Language Models on Edge AI Systems

During my undergraduate thesis, I built a profiling framework from the ground up to measure how much power Vision-Language Models draw when run at the edge, and used it to profile Gemma 3 running on a Raspberry Pi 5 via Ollama.

01

The problem

Language Models require a lot of compute and therefore consume significant power (W). To help IoT developers build LLM-based applications on the edge, they need to know how much power their workload will consume so that they can attach the correct battery. The existing literature did not provide a framework to comprehensively capture power consumption in a way that could be analyzed efficiently, so I decided to develop one from scratch. Although the implementation targets the Raspberry Pi 5 using Ollama, the framework can be applied to any model, on any inference engine, on any device.

02

Gaps in the existing literature

I started by identifying gaps in the existing literature, and found five.

Lack of subsystem monitoring

No visibility into which components (CPU, RAM) are consuming the most power, which is what helps answer where a workload’s draw actually comes from.

Lack of measurement accuracy

No way to know whether the measurements from existing methods can actually be trusted.

No custom sampling rate

USB power meters are usually limited to a fixed rate set by the manufacturer, which pushed researchers toward visually recording power consumption, introducing significant human error.

No cost-effective solution

High-end meters with accurate, high sampling rates and real-time monitoring cost $600–$1,400, still can’t monitor CPU/RAM, and require electrical engineering knowledge to operate.

No real-time monitoring dashboard

With many hardware and software components interacting, there was no visual way to catch problems early during experimentation.

03

Three power meters, combined

I selected and combined three measurement methods to address the gaps above.

IoT-based power meter

~$20 USD

Total power consumption of the device under test. Cost-effective, and exposes a WebSocket interface for real-time measurement.

Software-defined power meter

Free · built into the Pi 5

Measures the CPU, RAM, and other on-device components. Supports a custom sampling rate and real-time measurement by extracting values directly.

Plug-based power meter

Verification

Used to verify the accuracy of the IoT-based power meter via its onboard display, confirming it isn’t faulty.

This led to a profiling pipeline built from the ground up using all three techniques for Ollama, giving researchers and IoT developers a way to analyze power consumption both in real-time and after the fact.

04

Implementation

Software-defined power meter: vcgencmd

Built on the vcgencmd shell command, which is specifically designed for the Pi 5 to query power data directly from the GPU for components like the CPU, RAM, Wi-Fi chipset, and system power lines. That data is raw and unusable for analysis as-is, so I extracted the power values with regex and saved them to a CSV file for analysis.

IoT-based power meter: Shelly Plug US Gen4

Captures the Pi 5’s total power consumption. I configured a WebSocket connection from my MacBook to retrieve power values in real time and store them in a CSV file for later analysis, written in TypeScript.

Plug-based power meter: redundant verification

Used as a redundant method to verify the IoT-based meter’s accuracy via its onboard display, confirming it was operating correctly.

Running profiler and inference concurrently

Written in Python, using the multiprocessing and subprocess libraries to run the profiler and the vision-language model inference simultaneously. I primarily profiled Gemma 3, but the profiler supports any open-source model available on Ollama.

05

Building the dataset

One of the most complex challenges was obtaining high-quality, consistent data suitable for profiling. The wide variation in quality and consistency across publicly available datasets meant I had to create my own. I purchased the Raspberry Pi Camera Module 3 and configured the Pi 5 to capture images of a driveway segment in front of my home, giving me full control over angle, quality, and frequency. I captured over 5,000 images, which introduces a wide range of features that can influence power behavior and are important to document in the research.

Labeling that many images quickly, under a tight deadline, was its own problem. I built a custom labeler in Lovable and bound keyboard keys to labels so I could hold down keys to label rapidly. To reduce human error, I disabled mutually exclusive options: for example, labeling an image as daytime automatically disabled all nighttime-related labels.

06

Synchronization & monitoring

Syncing the IoT meter with the software-defined meter

Programmatically synchronizing the two power meters was essential for consistency across the collected data. Without it, I’d have had to manually start the IoT meter from the command line and separately trigger the Python script, causing timestamp misalignment. I solved this with an HTTP server on the Pi 5 that signals the IoT meter to begin measuring, keeping timestamps and values aligned.

Real-time monitoring dashboard

I configured a Prometheus server on my MacBook and Grafana Cloud to extract power metrics for the Pi 5’s subsystems as well as total device power, enabling real-time monitoring and early detection of anomalies during experimentation.

07

The framework, end to end

  1. Collect the data that will be power profiled.
  2. Choose an inference engine on the device under test.
  3. Integrate and sync the DUT power profiler with the subsystem profiler.
  4. Run the power profiling method based on the system: nvidia-smi, Intel RAPL, or vcgencmd on the Raspberry Pi 5.
  5. Collect the data.
  6. Structure the data, if it is unstructured.
